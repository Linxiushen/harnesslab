## 一面：项目深挖回答

### 1. Message Window 还是 Token Window？

“线上以 Token Window 为主，因为不同消息长度差异很大，固定消息数无法保证模型上下文不溢出；
Message Window 只用于短会话快速路径。裁剪时不是逐条硬切，我会保留 system 消息、最近用户意图和完整的
assistant-tool-result 关联组，并预留输出 Token。旧内容先结构化摘要，再把可长期复用的事实写入长期记忆。
HarnessLab 的 `ContextCompiler` 同时实现了两种窗口，并测试了 system 保留、输出预留和超限丢弃。”

### 2. Redis TTL 怎么定？

“TTL 不是拍脑袋定一个数字。我会分三层：活跃会话用滑动 TTL，任务快照用业务 SLA 对齐的绝对 TTL，
需要审计的事件进入独立事件存储。具体值由会话重访分布、恢复目标、合规删除要求和内存成本决定。
写入时带版本和 `expires_at`，后台先删过期记录，再按重要度和最近访问淘汰，避免 Redis 变成永久数据库。”

### 3. 并发会话冲突怎么处理？

“会话状态使用 `conversation_id + version` 做乐观并发控制，更新是 CAS；冲突后读取最新版本并重新合并，
不能用 last-write-wins 覆盖工具结果。工具侧再使用 idempotency key，防止模型重试导致支付、发信等副作用重复。
HarnessLab 的长期记忆更新要求 `expected_version`，旧版本会明确抛出 `MemoryConflict`。”

### 4. 长期记忆越来越多、检索越来越不准怎么办？

“先区分事实、偏好、事件和临时上下文，不把所有对话都进向量库。写入前归一化去重并设置 TTL、重要度和命名空间；
召回用向量语义 + BM25/关键词 + recency + importance 混排，然后做阈值、去重和重排。线上监控 Recall@K、
无关记忆率、重复率和每用户存储量。HarnessLab 的无依赖参考实现采用 lexical/recency/importance 混排、
指纹去重、TTL、容量上限和乐观锁；生产适配器可把 lexical 层替换成向量 + BM25。”

### 5. Token 溢出完整方案是什么？

“请求前先估算 Token，并给输出和工具结果预留空间；按优先级保留 system、安全策略、当前目标、最近完整工具链；
较老对话做结构化摘要，事实下沉长期记忆，大文档走检索而不是整篇塞入。仍然超限时拒绝或拆成子任务，
绝不静默截断关键指令。每次编译记录 dropped messages、输入 Token 和原因，方便回放。”

### 6. 单用户成本与百万流量怎么控？

“先回答公式，不编数字：`日成本 = 输入 Token × 输入单价 + 输出 Token × 输出单价 + 工具/检索成本`。
线上按 tenant、user、workflow、model 四个维度记账，看 p50/p95 和成功任务成本，而不是只看平均 Token。
治理顺序是前置 Token 估算、缓存、模型分层路由、上下文压缩、并发配额、硬预算和熔断降级。
HarnessLab 的 `BudgetLedger` 同时限制输入、输出、工具次数、估算美元成本和墙钟时间。真实面试时把你业务的
DAU、日均调用、Token 和单价代入，不能把 Demo 的合成成本当线上数据。”

### 7. 恶意长文本怎么限制？

“入口按字节、字符和估算 Token 三层限长，解压前检查压缩比；再做单用户滑窗、租户预算、并发上限和请求超时。
超限在模型调用前返回明确错误并记录 abuse reason。Prompt 内容还要过注入和敏感信息检测。
项目里 `estimate_tokens` 与 `SlidingWindowRateLimiter` 已进入 `traffic-abuse-guardrail` 评测。”

### 8. 为什么选基座而不是微调？

“先做约束门槛再评分，而不是先选模型再找理由。硬门槛包括上下文、工具成功率、安全、p95 延迟、质量和单请求成本；
过门槛后再按任务权重打分。只有当领域错误稳定、可标注数据充足、收益能覆盖训练和回归成本时才做 SFT。
工具型 Agent 常见情况是微调模型领域回答更好，但 tool-call schema 稳定性下降，此时宁可选基座。
HarnessLab 的 `ModelSelector` 用合成 fixture 证明：SFT 质量更高，但工具成功率未过门槛，所以选 general base。
评测数据要来自真实流量分层抽样、长尾故障、对抗样本和人工金标，并保留独立回归集。”

### 9. 线上故障具体怎么回答？

用固定结构：症状与影响 -> 定位证据 -> 根因 -> 改动的函数/逻辑 -> 灰度与回滚 -> 前后指标。

“我注入了三个可复现故障：仓库索引第一次返回 503，只对幂等读工具重试；主索引永久失败时把计划改到
last-known-good cache；生产 canary 违反 SLO 时停止部署，并逆拓扑补偿已经成功的写步骤。每个决策都有
`recovery.*` 事件，`agent-eval` 当前 9/9，测试 35 项通过。这些是工程回归指标，不冒充真实业务提升。
如果讲我自己的线上项目，我会换成真实的错误率、p95、成功率和成本前后值，并能指出具体 commit/函数。”

## 二面：商用 Agent 架构回答

### 10. 系统怎么拆？

“我拆成九个边界：Ingress 做鉴权限流；Router 判断简单/复杂；Planner 产出有类型的 DAG；Scheduler 做依赖、
并发、取消和超时；Policy Engine 校验 capability 和信任边界；Tool Gateway 做 schema、幂等和补偿；
Context/Memory 管短期与长期记忆；Budget/Model Selector 控成本与模型；Event/Eval 做追踪、回放和发布门禁。
模型只负责受约束的决策，不直接拥有工具权限。”

### 11. 模块怎么通信，为什么这样拆？

“同步控制路径走 Pydantic/JSON Schema 契约，状态变化写有序事件；大结果传引用，不在消息总线复制全文。
Planner 不直接调用工具，Scheduler 不解析自然语言权限，Policy 不持有业务执行逻辑。这样可以独立替换模型、
MCP 工具和存储，并能把同一计划重放到故障注入环境。”

### 12. 怎么区分简单任务与复杂任务？

“先用低成本、可解释的规则特征做 preflight：副作用、高风险域、多步骤语言、条件依赖、开放式研究和请求长度。
低分任务单工具直达，高分任务进入 Planner；边界样本再由小模型分类。路由结果必须记录 signal 和 score，
错误路由进入离线数据集。HarnessLab 的 `TaskRouter` 会输出分类、分数、证据和建议并发度。”

### 13. 拆解粒度怎么控制？

“一个 Step 应对应一个可独立验证、可超时、可重试或可补偿的业务动作。不能细到每个模型 Token，也不能粗到
‘完成整个订单’。副作用边界单独成 Step，写后必须跟验证门；DAG 在执行前检查未知依赖、重复 ID 和环。
粒度最终由失败隔离、可观测性和补偿成本决定。”

### 14. 何时重试、回滚、重规划？

“重试：瞬时错误 + 工具幂等 + 未超次数/时间/成本预算。回滚：前序副作用已成功、后序永久失败，而且有明确补偿语义。
重规划：原路径不可用但目标仍成立，例如主检索永久失败转只读缓存。权限拒绝、参数错误和预算超限默认终止，
不能盲目重试。HarnessLab 有 transient retry、fallback replan 和 reverse-order saga 三个独立场景。”

### 15. 多工具怎么配合？

“工具先变成有输入/输出 schema、权限、幂等性、超时、成本和 trust boundary 的节点；Planner 只连数据依赖，
Scheduler 执行 ready set 并限制并发。搜索与指标可并行，代码检查等待两者，写操作等待检查，部署等待测试。
工具输出先验证 schema 和注入风险，再允许进入下游。”

### 16. 工具权限怎么管？

“默认拒绝。服务端签发 HMAC capability token，绑定 subject、run_id、能力集合和过期时间；Policy 对每个工具计算
required capabilities，写工具额外需要 `tool.write`。Token 不能跨 Run 复用，篡改、过期和跨 Run 都拒绝；
外网工具再校验 egress allowlist。模型看到工具名称不等于获得权限。”

### 17. 怎么防 Prompt Injection 越权？

“把网页、检索和工具输出标成不可信数据，不允许它们改变 system policy。检测到指令覆盖、角色伪造、密钥外传或
工具升级语句时给结果打 taint；taint 可以供只读分析，但不能驱动写/部署工具。即使漏检，capability 最小权限仍是
第二道边界。项目的 injection 场景会识别恶意检索结果，并在 deploy 前由策略层拒绝。”

## 负责人面：认知回答

### 18. Agent 是长期拐点还是热点？

“交互形态有热点成分，但‘模型从回答转向在约束下执行任务’是长期变化。真正落地不是通用自主智能体，而是输入、
工具、责任边界和成功指标明确的工作流，例如研发运维、客服处置、企业知识操作、供应链和内容生产。
判断一个方向能否长期成立，我看任务频次、人工成本、数据闭环、错误可恢复性和责任是否能界定。”

### 19. 你的差异化是什么？

“我的差异化不是会调 LangChain，而是能把 Agent 做成可运营的软件系统：模型/工具契约、权限、预算、并发、重试、
补偿、回放和评测是一套完整控制面。HarnessLab 不是 PPT 架构，它有 5 个故障场景、9 项离线门禁、公开 API/CLI、
Trace Contract 和 35 项测试。面试官可以直接注入故障验证我的说法。”

### 20. 未来 1-2 年瓶颈是什么？2B 还是 2C？

“模型能力仍会提升，但大多数商业项目近期瓶颈在工程与组织：可靠工具数据、权限责任、评测、成本、流程改造和
客户愿意为结果付费。2B 更可能先在窄场景跑通收入，因为价值和采购预算可量化，但销售、集成和合规周期长；
2C 分发快，却面临留存、同质化和推理成本。我的策略是先做高频高价值的 2B 楔子，同时保留可产品化的通用控制面。”

### 21. 从零带业务线，第一步做什么？

“第一步不是招人，也不是选框架，而是选一个可付费的窄工作流，和 5-10 个目标客户确认当前人工流程、错误成本、
成功指标和责任边界，做出基线 P&L。随后用两周做可回放原型，只有达到质量、时延、安全和单位成本门槛才扩团队。
最小团队按问题组建：一个懂业务和交付的人、一个 Agent/后端工程师、一个评测数据工程师；安全和前端按场景补齐。
商业化同时设计，因为没有成功指标、计费单位和数据闭环，技术 Demo 不会自然变成业务。”

## 40 秒项目自我介绍

“我主要做 Agentic 应用工程，但重点不是套框架，而是把模型执行做成稳定、可控、可回归的系统。
我做的 HarnessLab 把任务路由、DAG 调度、工具 capability、短长期记忆、Token/成本预算、重试/重规划/补偿、
Prompt Injection 隔离和 Trace Contract 放进同一个控制面。项目有 DeepSeek/OpenAI-compatible 适配边界、
API、CLI 和可视化工作台；故障注入评测 9/9、测试 35 项通过。面试中我可以直接演示主索引 503、备用计划、
生产 canary 失败回滚和恶意检索结果无法触发部署，而不是只讲框架名。”

## 不能伪造的内容

- 视频中的公司、轮次和问题来自讲述者个人经验，不应表述为官方统一流程。
- 项目里的价格、流量、延迟和故障数据是确定性 fixture，不能写成真实生产成绩。
- 面试中的“提升百分比”必须来自你能解释口径、样本量、时间窗口和回滚方案的真实项目。
- 向量检索在本文是生产设计建议；当前开源参考实现为了离线可重复，使用 lexical hybrid store。
